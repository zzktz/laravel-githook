# Laravel Gitee / GitHub Webhook 自动更新包方案

## 1. 目标

开发一个可通过 Composer 安装的 Laravel 扩展包。Gitee 或 GitHub 仓库发生约定的推送事件后，对应 Webhook 调用宿主项目提供的 API；扩展包完成来源方认证、仓库和运行环境检查，再从远程仓库获取指定分支代码并更新部署目录。

目标框架为 Laravel 8 及以上版本（包含 Laravel 8）。扩展包不绑定某一个业务项目，路由、配置、部署逻辑和响应格式由包提供，宿主项目通过配置选择仓库、分支及更新策略。

## 2. 边界与基本约定

- 包负责接收 webhook、校验请求、执行安全检查、调用 Git 更新、记录结果并返回 HTTP 响应。
- 包不负责创建服务器、安装 Git、配置 Gitee/GitHub、管理 SSH 密钥或配置 Web 服务器；这些属于部署环境准备。
- 仅允许更新预先配置的仓库和分支。请求参数不得任意指定本地路径、远程地址、Git 命令或部署命令。
- 默认采用显式配置的部署目录和远程仓库；不从 webhook payload 中直接信任路径或 URL。
- 默认部署策略应为受控的 `fetch` + 指定分支更新。是否执行强制重置、是否保留本地改动必须由配置明确决定，不能静默覆盖未提交文件。
- Webhook 接口使用 HTTPS，并设置共享密钥；不要把密钥放进 URL、日志或响应正文。

## 3. Composer 包结构建议

包名建议：`vendor/laravel-githook`（发布前确定真实 vendor 名称）。遵循 PSR-4，支持 Composer 自动发现 Service Provider。

```text
src/
  GithookServiceProvider.php
  Http/Controllers/WebhookController.php
  Http/Middleware/VerifyWebhook.php
  Services/DeploymentService.php
  Services/GitClient.php
  Checks/...
  Events/DeploymentSucceeded.php
  Events/DeploymentFailed.php
  Exceptions/...
config/githook.php
routes/webhook.php
tests/
```

Service Provider 注册配置、路由和必要的容器绑定。路由前缀、middleware、controller、配置发布均通过 Laravel 常规机制实现，避免要求宿主项目复制包内源码。依赖声明采用 Illuminate 组件的兼容范围覆盖 Laravel 8 及以上版本；具体版本约束需在实现时依据 Laravel 8 的 PHP 版本要求和各 Illuminate 组件版本验证，避免只在最新 Laravel 上可安装。

## 4. 请求与更新流程

1. Gitee 或 GitHub 向各自配置好的 POST API 发送 webhook。
2. 请求入口检查 HTTP 方法、Content-Type、请求体大小及 JSON 格式。
3. 按 provider 验证请求：Gitee 校验 `X-Gitee-Token`；GitHub 使用配置密钥对原始请求体计算 HMAC-SHA256，并与 `X-Hub-Signature-256` 常量时间比较。再检查事件类型和来源 IP（可选）。
4. 解析仓库标识和推送 ref；校验仓库与配置匹配，并将 ref 映射到允许更新的分支。拒绝 tag、未知分支和未授权仓库。
5. 获取部署锁，阻止同一部署目录的并发更新；若锁被占用，返回明确的冲突响应，不启动第二次更新。
6. 执行部署前检查（见第 5 节）；任何失败均停止后续写操作并给出可诊断的错误码。
7. 通过参数化的进程 API 调用 Git，而非拼接 shell 命令。验证 Git 可执行、工作目录安全、worktree 有效、remote 与配置一致，并从远程 fetch 目标分支。
8. 按策略更新工作树。若要求工作树干净则先检查；只有显式启用覆盖策略时才允许 reset/清理，且配置说明其会丢弃本地改动。
9. 执行配置允许的更新后动作（例如 Composer install、Laravel 缓存处理、迁移或自定义部署步骤）。自定义动作应限定为管理员配置的命令，不接受 webhook 输入；命令超时、输出大小和失败行为可配置。
10. 进行部署后健康检查；记录部署结果、提交哈希、耗时和失败阶段，释放锁，并返回统一 JSON 响应。

建议提供同步模式作为首版，适合耗时可控的部署；后续可提供队列模式应对较长任务。同步模式需设置明确的 Git/命令超时，并在超时时可靠释放锁。若部署耗时可能超过 webhook provider 的等待限制，应切换为快速验签后投递队列、返回已接受状态的模式。

## 5. 条件检查清单

### 5.1 Webhook 请求检查

- 请求方法为 POST，Content-Type 合法，body 大小不超过配置上限。
- JSON 可解析，关键字段存在且格式正确。
- Gitee 共享 token 与服务端密钥使用 `hash_equals` 比较；GitHub 用原始 body 和 Secret 验证 SHA-256 HMAC 签名。
- 事件类型属于允许列表（例如仅 push）；若配置了来源 IP 白名单则匹配后才继续。
- payload 中的仓库标识匹配配置；推送分支在允许列表内。不得把任意 ref、仓库 URL 或路径直接传入命令。
- 可选地按 GitHub `X-GitHub-Delivery` 或 Gitee 投递 ID 做重放去重；首版依靠分支锁和幂等更新。

### 5.2 主机与代码目录检查

- Git 已安装且版本/能力符合要求；运行 PHP 的用户拥有必要读写权限。
- 部署目录为绝对路径，真实路径位于管理员允许的根目录内；拒绝空路径、根目录、符号链接逃逸等危险目标。
- 目录存在且是预期 Git worktree；配置 remote 与预期仓库一致，当前分支/目标 ref 合法。
- 工作树状态符合更新策略；默认检测本地未提交改动并拒绝覆盖。
- 磁盘空间、目录写权限、锁文件位置可用；部署锁可原子获取并可在异常时释放。
- SSH/HTTPS 远程认证由部署环境提供；包不记录凭据，不在异常中输出带凭据的 URL。

### 5.3 部署后检查

- Git 更新完成且 HEAD 指向预期提交。
- 配置的后置步骤均成功；必要的 Laravel 缓存重建、迁移等由项目选择启用，默认不擅自执行破坏性迁移。
- 可配置健康检查（例如本地 HTTP URL 或自定义回调）成功；检查失败时记录为部署失败并按策略告警/回滚。
- 回滚能力在首版可限定为保留更新前提交哈希并允许管理员手工回退；自动回滚作为后续能力评估，尤其要考虑数据库迁移不可逆情况。

## 6. 配置设计草案

建议发布 `config/githook.php`，敏感值通过环境变量提供。字段命名实现时可调整，但配置职责应保持清晰：

| 配置项 | 用途 |
| --- | --- |
| `enabled` | 总开关，关闭时拒绝部署请求 |
| `route` / `middleware` | webhook 路径及额外中间件 |
| `providers.gitee` / `providers.github` | provider 启用状态、密钥、允许事件和来源 IP 白名单 |
| `repositories` | Gitee/GitHub 仓库标识、remote、部署目录、允许分支及各 provider 密钥的映射 |
| `deployment.strategy` | 更新策略及本地改动处理规则 |
| `deployment.lock_path` / `lock_timeout` | 锁文件与获取等待时间 |
| `git.binary` / `git.timeout` | Git 可执行文件和超时 |
| `commands.before` / `commands.after` | 管理员配置的部署前后命令及超时 |
| `health_check` | 可选健康检查方式和超时 |
| `logging.channel` | 部署日志通道；日志脱敏策略固定生效 |
| `response` | 对外响应中是否返回提交哈希等非敏感信息 |

配置示例（仅表达结构，字段以实现版本为准）：

```php
return [
    'enabled' => env('GITHOOK_ENABLED', false),
    'providers' => [
        'gitee' => ['secret' => env('GITHOOK_GITEE_SECRET')],
        'github' => ['secret' => env('GITHOOK_GITHUB_SECRET')],
    ],
    'repositories' => [
        'main-app' => [
            'remote' => env('GITHOOK_REMOTE'),
            'path' => base_path(),
            'branches' => ['main'],
        ],
    ],
    'deployment' => [
        'strategy' => 'fast_forward',
        'require_clean_worktree' => true,
        'timeout' => 120,
    ],
];
```

## 7. 安全与失败处理

- 请求认证失败统一返回 401/403，避免泄漏密钥或仓库是否存在等细节。
- 参数和命令分离传递，禁止 `shell_exec` 拼接用户输入；Git 分支名需格式校验并映射到配置白名单。
- 只允许管理员配置的目标目录、remote、分支和钩子命令；接口不提供任意命令执行能力。
- 防止并发部署、路径穿越、符号链接逃逸、命令注入、日志泄密和错误堆栈暴露。
- 对部署结果记录结构化日志：请求/投递 ID（若有）、仓库别名、分支、旧/新 commit、各阶段耗时、结果码；不记录 secret、认证头或敏感 URL。
- 设计稳定的错误码和 HTTP 状态：请求无效、认证失败、条件不满足、已有部署运行、部署步骤失败、健康检查失败、成功。外部响应简洁，详细原因只进受控日志。
- 部署更新应可重复执行；遇到部分成功时记录失败阶段和当前 commit，避免错误地报告成功。回滚和数据库迁移需单独界定策略。

## 8. Laravel 兼容性与接口

- 使用 Service Provider 自动发现；支持显式手动注册作为备用方式。
- 路由注册、配置发布、中间件、日志、事件、异常处理采用 Laravel 8 可用 API，不使用仅新版本存在的语法/API。
- 依赖约束覆盖 Laravel 8 到当前计划支持的版本；CI 至少覆盖 Laravel 8 和一个较新主版本，并按 PHP 版本矩阵安装测试。
- 对外提供可选部署成功/失败事件和部署服务接口，方便宿主项目扩展通知、审计或自定义检查。
- API 响应采用 JSON，成功响应包含状态、仓库别名、分支、commit（如启用）；错误响应包含稳定错误码和 request ID。

## 9. 测试与验收标准

- Composer 在 Laravel 8 及以上目标版本可解析安装；服务提供者能自动发现，配置和路由可按文档启用。
- 对缺失/错误密钥、错误事件、畸形 JSON、超大请求、未知仓库、未允许分支、禁用状态的请求均拒绝且不执行 Git。
- 对缺 Git、非 worktree、remote 不匹配、目录不可写、工作区有改动、锁冲突、命令超时等场景给出预期错误，并确保锁释放。
- 用临时本地 bare Git 仓库验证 fetch 与更新路径，不依赖真实 Gitee 网络；覆盖重复 webhook 和并发请求。
- 验证 Git 参数安全、路径边界、日志脱敏、HTTP 状态码和 JSON 响应。
- 部署成功后 commit 与远端目标一致；任一步骤失败时不得返回成功。
- 文档说明安装、配置 Gitee/GitHub Webhook、HTTPS 与密钥设置、权限/SSH 准备、升级兼容和故障排查。

## 10. 分阶段实施建议

1. **包骨架**：Composer 元数据、PSR-4、Service Provider 自动发现、配置和路由发布，先验证 Laravel 8 安装。
2. **Webhook 入口**：请求解析、共享密钥校验、事件/仓库/分支白名单、统一 JSON 响应和错误码。
3. **Git 与部署检查**：参数化 Git 客户端、目录/remote/worktree 检查、干净状态策略、部署锁、超时控制。
4. **更新与扩展点**：目标分支 fetch/update、可配置后置动作、事件、日志脱敏及健康检查。
5. **兼容与发布**：Laravel/PHP CI 矩阵、临时 Git 集成测试、安全审查、安装和运维文档，准备 Packagist 发布。

## 11. 需要在实现前确认的产品决策

以下项可先按括号中的建议实现，之后由配置覆盖：

- 更新对象是服务器上的现有 Git checkout（建议首版采用），还是由包自行 clone 到 release 目录并切换软链接？
- 默认更新策略采用快进更新并拒绝本地改动（建议），还是允许强制重置工作树？
- 更新是否需要在 HTTP 请求内同步完成，还是首版直接采用队列异步执行？建议先提供同步实现并限制超时，同时保留可扩展的队列接口。
- 是否把 Composer install、缓存清理/重建、数据库迁移列入首版可配置步骤？建议可配置但默认关闭迁移。
- 首版支持一个 webhook 密钥对应多个仓库，还是每个仓库独立密钥？建议配置支持按仓库单独密钥，并提供全局默认值。
